# Fallstack Concept Log

## Product Target

Target surface: **a Reddit Devvit Web game using Interactive Posts**.

Required product qualities:

- **Delightful UX**: exciting layout/theme, easy and fun to uncover.
- **Polish**: close to publishable, self-explanatory from the first session, Devvit Rules compliant.
- **Reddit-native**: community-minded, fresh, identity-driven, not just Reddit references.
- **Return hook**: reason to return regularly through anticipation, goals, evolving state, or fresh opportunities.

Important warnings to design against:

- No obvious AI slop.
- No on-the-nose Reddit theming.
- No literal "hook" gimmick.
- Avoid common ideas unless the execution is unusually distinct.
- Polish and mobile quality matter.

## Lessons From Previous Direction

The previous concept direction is still useful as a warning system.

Keep:

- one-line pitch clarity,
- shared community object,
- funny failure,
- comment fuel,
- daily/recurring return loop,
- self-explanatory first session.

Avoid:

- too much pre-explanation before play,
- disconnected role minigames,
- game state that lives mainly in comments,
- systems that feel like planning dashboards,
- scope that depends on many interacting features before the hook works,
- mobile layouts that require too much reading.

Current read:

> Fallstack works only if the first touch is immediately physical and the shared failure artifact is visible within seconds.

## Settled Grill Decisions

### 1. Primary Hook

Decision:

> Fallstack is primarily a shared community mutation game, expressed through a one-button precision climber.

Implication:

- The core hook is not "jump up a tower."
- The core hook is "the level is made out of everyone else's failures."
- Every major feature must serve visible shared mutation, comment material, retention, or arcade readability.
- If a feature only improves solo platforming, it is secondary.

Product rationale:

- This protects the idea from being dismissed as a common simple platformer.
- It directly supports the Reddit-y, Hook-y, recurring-content, and user-contribution criteria.

### 2. Failure Mutation Model

Decision:

> Failure creates a contextual object that is immediately readable as helpful, but repeated failure in the same zone can distort it into a curse.

Concrete behavior:

- First few failures near a jump create help: Corpse Stack, Mercy Nail, Ghost Platform, warning arc.
- Too many repeated failures in one zone change the zone state toward Haunted or Cursed.
- Successes push the zone toward Reinforced or Stabilized.

Design invariant:

> Failure should help, but accumulated failure should distort.

Why:

- If failure only helps, the tower becomes easier and loses tension.
- If failure mostly harms, players feel like they are griefing the subreddit.
- The strongest Reddit dynamic is mixed blame and gratitude: "your corpse saved me" and "who cursed this ledge?" both need to be true.

### 3. Input Model

Decision:

> The player uses Jump King-style controls: Left/Right Arrow keys to face or move, and press/hold Spacebar to charge the leap. No mouse, no dragging, no dropping objects, and no mouse-based aiming.

Implications:

- The core skill is commitment: choose direction, hold Space for power, release into a risky arc.
- The game should not depend on cursor precision.
- The player should not place artifacts manually.
- Failure artifacts are generated by play, not edited onto the board.
- The UI should avoid looking like a builder, planner, or dashboard.
- The game can lean on a known control grammar while making the shared mutation layer the distinct hook.

Important tension:

- Devvit iframe use includes mobile contexts, so keyboard-only controls cannot be the only production input.
- The mobile version needs an equivalent on-screen control scheme that preserves the same commitment loop without becoming drag-aiming.

Recommended implementation framing:

> Keyboard: Arrow keys + hold/release Space. Mobile: left/right buttons + hold/release jump button. No mouse. No drag. No manual artifact placement.

### 4. Platformer Clone Risk

Decision:

> Jump King-style controls are acceptable only because the differentiator is the shared mutable tower, not the movement model.

Positioning rule:

- Do not pitch this as "a hard climbing game."
- Pitch it as "a subreddit's failures physically rewrite today's climb."

Required proof in the first session:

- The first screen must show existing community artifacts before the player jumps.
- The player's first fall must visibly alter the tower or zone state.
- Mutation history is more important than a generic leaderboard.
- If a first-time player can play for 10 seconds and describe it only as a platformer, the design failed.

Reason:

- Familiar controls reduce onboarding friction.
- The product-defining part is the Reddit-native shared mutation layer.

### 5. First 10 Seconds

Decision:

> The first viewport must already contain a cursed community artifact, a readable reason it exists, and a promise that the player's next fall can change the tower too.

Required opening beat:

- Header: "Today's tower has 37 failed climbs in it."
- Visible starting zone contains 2-3 artifacts: Corpse Stack, Ghost Platform, Cursed Brick, Mercy Nail, or Lantern Trail.
- At least one artifact explains its origin in-place: "14 falls made this foothold."
- The player starts near a jump where an artifact is clearly useful or dangerous.
- After the first fall, the game shows: "Your fall added +1 to Moon Shelf. 2 more falls will spawn a Mercy Nail."
- Controls stay compact: "Arrows move. Hold Space. Release to leap."

Reason:

- The shared mutation hook cannot wait for a result screen.
- A first-time player should understand that the tower is community-shaped before making the first input.

### 6. Fall And Respawn Rule

Decision:

> Falling ends the current attempt, records a mutation, then respawns the player at the latest checkpoint.

Concrete rule:

- A run is one climb attempt until the player falls below the current zone's safe recovery line.
- Minor bonks and bad landings do not end the run by themselves.
- Falling past the bottom of the current zone ends the attempt.
- The mutation is recorded at the failure zone.
- The player restarts at the most recent checkpoint.
- The daily post keeps cumulative community state.

Reason:

- Full reset to floor 0 is too punishing for a Reddit interactive post.
- Continuous recovery makes failures less meaningful.
- Checkpoint respawn keeps frustration funny and creates more shared mutation events per session.

### 7. Shared State Aggregation

Decision:

> Every fall gives local feedback, but shared tower state is aggregated, thresholded, and rate-limited.

Concrete rule:

- Each fall is classified by zone and failure type: short jump, overjump, wall bonk, pit fall, helper overuse.
- The player sees immediate local feedback every time.
- Shared state updates counters and derived zone state, not a new object per fall.
- A visible artifact spawns or changes only when a threshold is crossed.
- Per-user or per-session contribution should be capped so one person cannot spam-corrode the tower.
- The game may say "your fall counted," but it should not literally place a new object every time.

Reason:

- Storing every fall as an object will clutter the tower.
- Literal writes invite griefing and noisy persistence.
- Aggregation preserves the social fantasy while keeping the surface legible.

### 8. V1 Failure Buckets

Decision:

> V1 uses four failure buckets only.

Buckets:

- `short_jump`: players undershoot a gap.
  - Artifact: Corpse Stack or Mercy Nail.
  - Meaning: repeated undershooting creates a small foothold.
- `overjump`: players overshoot and slam into or past the landing.
  - Artifact: Cursed Brick or cracked landing.
  - Meaning: repeated overshooting makes the far landing unstable.
- `wall_bonk`: players hit the same wall face.
  - Artifact: Ghost Platform or chalk impact mark.
  - Meaning: repeated wall hits reveal a temporary rescue platform or warning mark.
- `helper_overuse`: players rely too much on the same community aid.
  - Artifact: cursed helper variant.
  - Meaning: overused help becomes shaky or dangerous.

Reason:

- Four buckets are enough to make the tower feel alive without building a simulation.
- `pit_fall` can usually be derived from short/overjump location and should not be a separate v1 bucket unless implementation proves it necessary.

### 9. V1 Artifact Thresholds

Decision:

> V1 uses low thresholds for visible change, with strict per-zone caps.

Thresholds per zone and failure bucket:

- 1 fall: show a faint local mark only to that player.
- 3 matching failures: spawn a visible community artifact.
- 6 matching failures: upgrade the artifact.
- 10 matching failures: mark the zone Haunted or Cursed.
- 3 successful clears after a curse: downgrade the curse or stabilize the route.

Per-zone caps:

- 1 helpful artifact.
- 1 cursed or hazard artifact.
- 1 route hint or ghost arc.
- 1 zone state badge.

Reason:

- Low thresholds make the tower feel alive with small traffic.
- Caps prevent high-traffic posts from becoming unreadable.
- The specific numbers can be tuned, but v1 needs visible change within a first session or seeded daily state.

### 10. Seeded Daily State

Decision:

> Each daily tower can start from a believable seeded cursed state, and all player actions mutate real state from that point onward.

Concrete rule:

- The post opens with "37 climbers have already cursed today's tower."
- Starting state includes 2-3 visible artifacts and one cursed zone.
- The seed appears as normal game state, not as a visible fake mode.
- The player's own fall visibly increments or mutates something real.
- If real activity exists, merge it into the same counters rather than replacing the seed.

Reason:

- An empty tower hides the shared-mutation hook.
- Fake-looking seeded state hurts polish and trust.
- Seeded state is acceptable when it presents the intended daily state as the product's natural state.

### 11. Retention Loop

Decision:

> Each day has a new hand-authored tower seed plus a community-authored final state, and the next day opens with yesterday's most infamous curse memorialized.

Concrete loop:

- Today: climb and mutate the current tower.
- During the day: the subreddit tries to stabilize cursed zones and push the highest checkpoint.
- End of day: result card names highest climber, most cursed zone, most useful Corpse Stack, and cleanest stabilizer.
- Tomorrow: a new tower layout appears, but one relic from yesterday returns as flavor or a small mechanical modifier.
- Comments naturally become: "we cursed Moon Shelf yesterday," "today's tower is worse," "who stabilized the bell room?"

Reason:

- Daily reset alone is weak.
- Persistent identity through remembered failures makes the game Reddit-native and Hook-y without heavy meta-progression.

### 12. Success And Stabilization

Decision:

> Success temporarily stabilizes a zone and can downgrade curses, but it should not permanently erase the community's failure history.

Concrete rule:

- A successful clear increments `successfulClears`.
- 3 clears after a curse downgrade `Cursed` to `Haunted`.
- 6 clears stabilize the route for the rest of the day.
- Stabilized artifacts become safer, but remain visible as history.
- The result card credits the players who stabilized the zone.

Reason:

- If success erases failure, the funniest community evidence disappears.
- If success cannot help, skilled players feel irrelevant.
- Stabilization gives good players prestige while preserving the "we made this mess" story.

### 13. Tower Generation And Summit

Decision:

> V1 should use procedural tower generation, but it must be finite, seeded, validated, and built from constrained chunks. It should not be unconstrained endless randomness.

Definition:

- Procedural generation means the tower layout is created algorithmically from rules, seeds, chunks, difficulty curves, and artifact slots.
- It does not have to mean endless generation.

V1 target:

- One daily tower seed.
- A finite summit.
- 3 stacked visual themes or biomes inside the same climb.
- Generated from constrained handcrafted chunks or templates.
- Each generated tower must pass basic reachability and readability validation.

Why this constraint exists:

- A fully random Jump King-style tower can generate impossible, unfair, or ugly jumps.
- Judges must not encounter a broken daily layout.
- Procedural variety helps retention, but fairness and polish matter more than novelty.

When someone clears the summit:

- They become the day's first clear title holder.
- Their successful route can become a Lantern Trail for others.
- The tower does not close for everyone else.
- Other players can still beat clear time, climb with fewer falls, stabilize cursed zones, create or repair artifacts, and reach the summit through a mutated route.
- The result card should celebrate first clear, cleanest clear, highest climber if uncleared, best stabilizer, and most cursed zone.

### 14. Procedural Generation Type

Decision:

> V1 uses hybrid procedural generation, but chunk-first.

Definition:

- Hand-designed tower chunks provide the core geometry and intended jump patterns.
- The generator stitches chunks together by seed, theme, difficulty, and connector compatibility.
- Small procedural variation can change ledge widths, decoration, artifact slots, hazard state, or theme dressing.

Why:

- This is procedural enough to support daily variety and a credible retention story.
- It avoids the highest-risk version of generating raw Jump King-style ledges from scratch.
- It lets the team validate chunks individually before composing a daily tower.

Rejected for v1:

- Fully unconstrained endless generation.
- Pure mathematical ledge placement without handcrafted constraints.

### 15. Theme Scope

Decision:

> V1 has 3 stacked tower themes, mostly visual, with one light mechanical identity per theme at most.

Example direction:

- Lower Ruins: forgiving stone ledges; introduces Corpse Stacks and Mercy Nails.
- Bell Shaft: narrower platforms; introduces wall-bonk Ghost Platforms.
- Moon Roof: unstable ledges; introduces Cursed Bricks and Wind Scars.

Constraints:

- No separate physics system per theme.
- No water, ice, or wind simulation in v1 unless it reuses existing movement rules.
- One global movement model.
- Theme-specific mechanics must reuse the four v1 failure buckets.

Reason:

- Three themes improve perceived scale and memorability.
- Three full mechanical rule sets would multiply balancing and implementation risk.

### 16. Mobile Controls

Decision:

> Mobile uses three fixed on-screen controls: Left, Jump, Right.

Concrete rule:

- Left button: hold to move or face left.
- Right button: hold to move or face right.
- Jump button: hold to charge, release to leap.
- Buttons stay fixed and large enough for thumbs.
- No drag aiming.
- No tap-to-place.
- Desktop uses keyboard as primary.
- Optional clickable controls can remain visible for testing and mobile parity.
- The tower viewport should not be covered by controls during critical jumps.

Reason:

- This preserves the Jump King commitment loop on touch screens.
- Gesture controls would make the game feel like a different game.
- Fixed controls reduce accidental inputs inside a Reddit post.

### 17. V1 Artifact Set

Decision:

> V1 uses exactly five artifact types.

Included:

- Corpse Stack: helpful foothold from repeated short jumps.
- Mercy Nail: tiny stabilizing peg after repeated failures at a choke.
- Ghost Platform: temporary translucent platform from repeated wall bonks.
- Cursed Brick: hazardous or shaky ledge from repeated overjumps or helper overuse.
- Lantern Trail: successful route hint from clean clears.

Deferred:

- Wind Scar.
- Crack Line.
- Bell of Shame as an in-level object.
- Spite Spring.
- Echo Block as separate from Ghost Platform.

Note:

- Bell of Shame can still exist as an end-of-day result-card award.

Reason:

- Five artifacts are enough for screenshots and comments.
- More would force players to learn a taxonomy before the hook lands.

### 18. Artifact Collision Semantics

Decision:

> Every artifact must clearly communicate whether it is solid, semi-solid, hazardous, or visual-only before the player touches it.

V1 artifact rules:

- Corpse Stack: solid platform or foothold.
- Mercy Nail: solid tiny ledge, but narrow.
- Ghost Platform: semi-solid platform, either temporary or limited-use.
- Cursed Brick: solid ledge with a timing hazard, wobble, or crumble delay.
- Lantern Trail: visual-only arc, no collision.

Reason:

- Precision climbing can be frustrating, but it cannot feel arbitrary.
- Ambiguous collision creates bad frustration rather than funny frustration.

### 19. Procedural Fairness Rules

Decision:

> Procedural towers are generated only from validated chunks, and each chunk must have a known baseline solution path that does not depend on helpful artifacts.

Generation rules:

- Each chunk has entrance and exit connectors.
- Each chunk declares min/max jump difficulty.
- Each chunk has at least one known clear path using only default geometry.
- The generator stitches compatible chunks only.
- After stitching, run a cheap reachability check from checkpoint to checkpoint.
- If validation fails, reroll or swap the chunk.

Mutation rules:

- Helpful artifacts may add alternate paths, but cannot be required.
- Cursed artifacts may make a path harder, but cannot block the only route.
- Shared mutation changes route feel, not baseline finishability.

Reason:

- The subreddit can curse the tower, but it must not permanently brick the daily climb.
- Judges should never encounter an impossible generated layout.

### 20. Shared State Shape

Decision:

> Shared state stores aggregated, deterministic daily tower data only.

Top-level state:

```text
dailySeed
towerVersion
zoneStates[]
leaderboard
summitClear
dailyRelic
```

Each `zoneState`:

```text
zoneId
themeId
chunkId
failureCounts: {
  short_jump
  overjump
  wall_bonk
  helper_overuse
}
successfulClears
activeArtifacts[]
curseLevel
stabilityLevel
lastMutationAt
topContributors
```

Do not store:

- every jump arc,
- every fall object,
- raw player movement logs,
- unbounded ghost trails,
- arbitrary user-generated text,
- per-frame physics data.

Reason:

- Deterministic generation plus compact mutation state keeps storage sane.
- The generated layout should come from seed plus chunk library, not from storing a huge map blob.

### 21. Player Identity And Blame

Decision:

> Name players for positive achievements, and anonymize or aggregate most failures.

Show usernames for:

- first summit clear,
- highest climber,
- cleanest clear,
- zone stabilizer,
- best recovery or contribution.

Avoid:

- "u/name caused the cursed brick" by default.
- personal public shame for repeated failure.

Artifact wording:

- Use "14 falls made this," not "u/name died here 14 times."
- Personal feedback can say "your fall counted."
- End card can include funny aggregate awards like Bell of Shame for a zone, not for a player.

Reason:

- The game needs comment material, but the target should be the tower, zone, or community event.
- Positive identity is safer and more motivating than naming failure.

### 22. Daily Result Card

Decision:

> The daily result card summarizes the day as a community story, not just a scoreboard.

V1 result fields:

- Tower name and seed.
- Summit status: cleared or uncleared.
- First summit clear: username and time/falls, if cleared.
- Highest climber, if uncleared.
- Most cursed zone.
- Most useful artifact.
- Best stabilizer.
- Total climbs, falls, and clears.
- Tomorrow hook: "Yesterday's Bell of Shame returns as a relic."

Optional if time allows:

- Small tower silhouette showing where the worst curse formed.
- One short share line suitable for comments.

Reason:

- The result card is how the game becomes Reddit-native outside the play session.
- It gives people something to argue about, celebrate, and remember tomorrow.

### 23. Role Of Reddit Comments

Decision:

> Comments amplify the game, but never contain required game state or required inputs.

Rules:

- The game state must be fully understandable inside the interactive post.
- Comments are for reactions, blame, celebration, route advice, and daily result discussion.
- No voting in comments to mutate the tower in v1.
- No hidden clues in comments.
- No requirement to read comments before playing.
- The app may generate or offer a shareable result line, but should avoid spammy automatic bot behavior.

Reason:

- This preserves the Reddit-native social layer without making comments carry the actual game.

### 24. Name

Decision:

> Product name: **Fallstack**.

Presentation:

> Fallstack: Cursed Tower

Usage:

- Fallstack is the product/app name.
- Cursed Tower can be the mode, subtitle, or first daily tower format.
- Individual daily towers can have names such as "Moon Shelf."

Reason:

- Fallstack implies accumulated failure.
- It is shorter and more ownable than Cursed Tower.
- It sells the core mechanic better than a generic fantasy name.

### 25. Visual Direction

Decision:

> Compact cursed diorama: readable silhouettes, chunky physical materials, minimal UI chrome, and artifact labels that feel stamped into the tower.

Rules:

- Side-view vertical tower, not a dashboard.
- Chunky stone, metal, and moon materials with strong silhouettes.
- Limited palette per biome, but not one-note.
- Artifacts are visually distinct by shape, not just color.
- UI overlays are sparse: zone name, climb/fall stats, current mutation.
- Avoid generic pixel-art fantasy unless executed very well.
- Avoid heavy cards, fake parchment overload, neon gradients, and lore paragraphs.
- The tower should be the hero, not the panels.

Reason:

- The first session depends on polish and immediate legibility.
- The game should look like a tactile object the subreddit damaged together, not a platformer template with labels added.

### 26. Rendering Technology

Decision:

> Use Phaser for the playfield if the build commits to physics-feeling movement, camera follow, collision, particles, and responsive input.

Why Phaser fits Fallstack:

- Jump King-style movement needs collision and tuning.
- Camera follow up a vertical tower is natural.
- Artifacts can be real physics or collision objects.
- Phaser helps the core feel tactile instead of DOM-like.
- Phaser has current official support and fits the game runtime better than a custom DOM or canvas loop.

Architecture constraint:

- Phaser owns the playfield.
- Devvit Web owns the post shell, server endpoints, state panels, result card, and persistent state calls.
- Do not build a custom engine unless Phaser integration fails.

Reason:

- Phaser is tied to core feel, not external positioning.

### 27. Architecture Split

Decision:

> Keep pure game rules, Phaser simulation, and Devvit Web persistence clearly separated.

Pure game logic module owns:

- tower generation,
- chunk selection,
- mutation threshold derivation,
- artifact derivation from zone state,
- scoring and result summaries.

Phaser scene owns:

- movement,
- collision,
- camera,
- jump and fall detection,
- rendering tower/artifacts,
- emitting events such as `fallRecorded`, `checkpointReached`, `summitCleared`.

Devvit Web shell/server owns:

- loading and saving shared state,
- compact stats and result panels,
- mobile controls,
- passing input state/events to Phaser when DOM controls are outside the Phaser scene,
- post lifecycle and persistence.

Constraint:

> Phaser should not directly own persistent Reddit state. It emits game events or calls typed `/api` endpoints, and the Devvit Web server decides what to persist.

Reason:

- Physics and rendering should stay separate from Devvit storage.
- Procedural and mutation logic should be testable without launching the canvas.

### 28. Persistence Timing And Concurrency

Decision:

> Persist only at attempt boundaries, using aggregated increments and merge-safe updates.

Concrete rule:

- During play, falls and checkpoints are local events.
- When a player falls below the zone recovery line, the attempt ends.
- The shell sends one mutation event: `{ dailySeed, zoneId, failureBucket, userIdHash/sessionId, timestamp }`.
- Persistence increments the relevant counter if the user/session has not exceeded contribution caps.
- Artifact state is derived from counters after the merge.
- If two players update the same zone, both increments can coexist.
- If exact compare-and-swap is unavailable, prefer additive counters and recompute derived artifacts instead of storing final object state directly.

Reason:

- Derived state is easier to merge than "place this exact platform at x/y."
- Additive counters avoid last-write-wins wiping out another player's contribution.

### 29. Anti-Griefing Contribution Caps

Decision:

> Cap mutation impact per user per zone per day, but keep personal play unlimited.

V1 caps:

- A player can attempt the tower unlimited times.
- Only the first 3 matching failure contributions per user per zone per day count toward shared mutation.
- Only the first 10 total failure contributions per user per day count globally.
- Successful clears and stabilizations also cap per zone so one strong player cannot instantly erase curses.
- Local feedback still appears after the cap.

Example capped feedback:

> Your fall was witnessed, but this zone has heard enough from you today.

Reason:

- One person should not be able to corrupt the shared state.
- The cap affects community mutation, not the ability to keep playing.

### 30. Layered Player Goals

Decision:

> Fallstack uses layered goals so bad, average, and excellent players all matter.

Goals:

- Personal goal: reach a higher checkpoint than the last attempt.
- Community failure goal: contribute to spawning or upgrading a helpful artifact.
- Community repair goal: stabilize a cursed zone.
- Skill goal: clear with fewer falls or faster time.
- Prestige goal: first summit clear, cleanest clear, or best stabilizer.
- Daily social goal: make the result card more interesting.

Reason:

- If summit clear is the only goal, most players are just bad climbers.
- Fallstack's strength is that failure changes the day while skill still earns prestige.

### 31. Camera And Viewport

Decision:

> Use a vertical follow camera with upward lookahead and short pre-jump framing.

Rules:

- Camera follows the climber vertically.
- Camera keeps more space above the player than below.
- While grounded, camera subtly biases toward the intended jump direction or next ledge.
- On charge, show the nearby landing area if possible, but do not reveal the whole tower.
- Checkpoints briefly settle or frame the next zone name and artifact state.
- Mobile controls occupy a fixed bottom safe area, and camera framing must account for it.
- Avoid tiny zoomed-out tower views during active play.

Reason:

- A vertical climber needs enough information for fair jumps.
- The tower should still feel tall and tense.
- A static full-tower view would be unreadable on mobile.

### 32. Difficulty Targets

Decision:

> The first daily tower should be hard enough to produce falls quickly, but forgiving enough that a new player reaches the first checkpoint in under 60-90 seconds.

Tuning targets:

- First fall likely within 10-20 seconds.
- First visible mutation feedback within 30 seconds.
- First checkpoint reachable by an average new player within 60-90 seconds.
- Summit should be hard but not streamer-hard.
- Early zones teach control and mutation.
- Later zones test mastery and community artifacts.
- Seeded artifacts should help new players experience success even if they are not good at platformers.

Reason:

- The game needs failure.
- The first session cannot depend on players loving punishing platformers.
- The first minute must show the loop, not just a skill wall.

### 33. Checkpoint Behavior

Decision:

> A checkpoint locks personal progress, contributes to zone stabilization, and briefly reveals the community state of the next zone.

Concrete behavior:

- Player respawn point moves to the checkpoint.
- The cleared zone gets a `successfulClear` contribution, subject to caps.
- If enough clears occurred, the zone downgrades curse or stabilizes.
- A compact checkpoint banner appears.
- The camera settles upward to preview the next zone.
- Player can continue immediately; no menu required.

Example banner copy:

- "Lower Ruins stabilized by 3 clean climbs."
- "Next: Bell Shaft, currently Haunted."

Reason:

- Checkpoints should feel like personal relief and community contribution at the same time.
- They give the tall tower a natural rhythm.

### 34. Mutation Copy Tone

Decision:

> Mutation feedback should be dry, compact, mildly cursed, and never verbose.

Good examples:

- "14 falls made this foothold."
- "Moon Shelf is Haunted."
- "Your fall counted. 2 more short jumps spawn a Mercy Nail."
- "Too many clean climbs. The curse weakened."
- "This brick remembers overconfidence."
- "Bell Shaft has heard enough from you today."
- "u/riverknife stabilized the Lower Ruins."

Avoid:

- long tutorial sentences,
- fake bot commentary,
- meme overload,
- mean personal shaming,
- lore paragraphs.

Reason:

- The copy should generate comments without becoming the game's main content.
- Short labels make the tower readable while giving it personality.

### 35. Procedural Fallback

Decision:

> If procedural generation is not stable enough for production, fallback to a locked known-good seed generated by the same chunk system.

Fallback behavior:

- Keep the procedural architecture.
- Use a fixed known-good seed for the published daily tower.
- Generate from the same chunk system, but lock the seed.
- Validate and polish that seed heavily.
- Still present it as today's tower.
- Unlock daily seed variation only after validation proves generated towers are fair.

Reason:

- This preserves the procedural claim and architecture.
- It protects the published build from a bad random layout.
- The fallback is not "throw away procedural generation"; it is "lock generation to a known-good daily seed."

### 36. Product Walkthrough Beats

Decision:

> Any product walkthrough must show the community mutation loop visually in the first 60 seconds.

Required beats:

1. Open the Reddit interactive post: "Today's tower has 37 failed climbs in it."
2. Show existing artifacts in the starting zone.
3. Play one jump and fail.
4. The fall increments a zone counter and previews or spawns an artifact threshold.
5. Respawn at checkpoint/start and use an existing community artifact.
6. Reach a checkpoint and stabilize a zone.
7. Briefly show the result card: most cursed zone, first/cleanest clear, tomorrow relic.
8. End on: "The level is made out of everyone else's failures."

Reason:

- The walkthrough should not spend time explaining architecture, procedural generation, or controls.
- It should make the shared mutation loop undeniable.

### 37. Scope Cuts

Decision:

> Do not build anything that competes with the polished shared-mutation climbing loop.

Hard cuts:

- Real endless mode.
- Full raw ledge procedural generation.
- More than 3 themes.
- More than 5 artifacts.
- Skins, cosmetics, or shop.
- Inventory or powerups.
- Complex relic system.
- Replays for every player.
- Comments-as-input.
- Subreddit voting mechanics.
- Multiplayer presence or realtime ghosts.
- User-generated tower chunks.
- Full moderation tools.
- Multiple game modes.
- Long tutorial or onboarding sequence.

Reason:

- These features compete with the actual product path: polished playable loop, visible shared mutation, mobile quality, and a clean daily story.

### 38. Pre-Implementation Proofs

Decision:

> Validate movement feel, generation validity, and mutation readability before full production.

Proof 1: Movement feel

- Devvit Web Phaser scene with Jump King-style movement.
- One screen of ledges.
- Tune jump charge and collision until it feels fair.

Proof 2: Generation validity

- Generate 10-20 seeded towers from chunks.
- Confirm checkpoint-to-checkpoint reachability.
- Lock one known-good seed for the daily path if needed.

Proof 3: Mutation readability

- One zone with Corpse Stack, Ghost Platform, Cursed Brick, and Lantern Trail.
- Simulate counters crossing thresholds.
- Confirm the player understands "falls changed the level" without reading a doc.

Reason:

- These are the three ways the concept can fail.
- UI polish cannot rescue bad movement, broken generation, or invisible mutation.

### 39. V1 Global Scope And Live Sync

Decision:

> In v1, “global” means one community-wide daily board for every Fallstack entry point in the same subreddit installation.

Concrete rule:

- The server derives board identity from authenticated installation/community context, UTC date, and tower version.
- The client cannot select a subreddit, board scope, Redis key, or display identity.
- Visible clients probe only board identity and revision every 15 seconds.
- An unchanged revision causes no full-board read or render work.
- A newer revision or daily board identity fetches the bounded snapshot, then applies collision changes only at a safe reconcile point.
- Cross-Reddit global state is not v1. It requires explicit approval for an external authority, abuse/privacy/security controls, availability ownership, and migration.

Evidence:

- Installed Devvit playtest `v0.0.20.2` accepted client A's hosted mutations from board `R37 → R39`.
- Independent signed-in client B retained its captured `R37`, then reconciled without reload to `R39` and the six-fall First Gap `Mercy Nail` through the normal poll path.

Reason:

- Devvit Redis is installation-scoped, so community-global is the strongest native authority boundary.
- Revision-first polling preserves the live community consequence without repeatedly deriving and transporting an unchanged board.
- Calling an installation-local board cross-Reddit global would be technically false.

## Pre-Grill Brainstorm (Historical)

> **Note**: Everything below this line was written before the grill sessions above. It is preserved as context for how the idea evolved. Where it contradicts a numbered Settled Grill Decision (§1–§39), the grill decision is canonical. See `AGENTS.md` for the current operating spec.

## Why We Pivoted

The previous concept became too complex for the actual Reddit games surface. It required explaining too many systems before the player could feel the hook.

The better direction is to start from a single physical toy:

> A frustrating one-button climbing game where every failed attempt changes the shared daily tower for everyone else.

This fits the Reddit interactive-post surface because it has:

- an immediate action,
- visible shared contribution,
- natural comments and blame,
- a daily reset,
- low content burden,
- a clear arcade hook.

## Core Pitch

> Everyone climbs the same daily tower. Every failed jump leaves something behind. Your fall might save the next climber, or curse the route for the whole subreddit.

Shorter:

> The level is made out of everyone else's failures.

## Core Loop

1. Open the daily tower post.
2. Use Left/Right to choose direction.
3. Hold Space to charge and release to leap.
4. Land higher, or fall.
5. A fall leaves a physical mark on the tower.
6. Future players see and use or suffer from that mark.
7. Reaching a checkpoint stabilizes that tower section.
8. End of day summarizes the subreddit climb.

## Why This Is Reddit-Native

- Bad players still contribute.
- Good players become visible legends by clearing cursed sections.
- The post changes as the community plays.
- Comments have natural material: "who cursed Moon Shelf?", "my corpse saved you", "beat my jump".
- The daily result can be screenshot-friendly: highest floor, most cursed spot, top climber, funniest fall.

## Shared Failure Artifacts

> *Superseded by §17 (V1 Artifact Set) and §18 (Artifact Collision Semantics). The final 5 artifacts and their collision rules are defined there.*

Early candidate list preserved for reference:

- **Corpse Stack**: repeated deaths create a small foothold.

- **Cursed Brick**: a helpful block becomes unstable after too many touches.
- **Lantern Trail**: successful players leave a suggested jump arc.
- **Mercy Nail**: many failures pin a tiny safe peg into the wall.

## Scaling Model

> *Incorporated into AGENTS.md § Scaling Model with the settled cap numbers from §9 and §29.*

Early thinking preserved for reference:

### 1 Player — seed believable state, first fall creates visible feedback.
### 10 Players — most contributions show, low thresholds.
### 50 Players — aggregate repeated events, cap visible artifacts.
### 100 Players — zone states (Quiet → Haunted → Cursed → Reinforced → Stabilized), anti-griefing caps engage.
### 500 Players — aggregated counters, capped artifacts, no sharding for v1.

## Open Questions

> *All resolved in grill sessions. Answers noted inline.*

- How much control does the player have in air? → **Light arrow-key nudge mid-flight. Not full air control.** (§3, settled post-grill)
- Does falling always end a run, or can the player recover? → **Fall below zone recovery line ends the attempt. Minor bonks do not.** (§6)
- How do artifacts avoid griefing? → **Per-zone caps, per-user contribution caps, cursed artifacts cannot block the only route.** (§9, §19, §29)
- How many artifacts can exist per checkpoint zone? → **1 helpful, 1 hazard, 1 hint, 1 badge.** (§9)
- What is the right balance between helpful and cursed failure? → **Failure helps early, accumulated failure distorts.** (§2)
- What makes the first 10 seconds funny? → **Existing community artifacts visible before first jump, fall feedback is dry and mildly cursed.** (§5, §34)
- What is the name? → **Fallstack.** (§24)
